# Install in the intended account, then test

Official documentation supports [account-owned plugin authoring](https://learn.chatgpt.com/docs/build-plugins) using Plugin Creator when available, and [local private marketplaces](https://developers.openai.com/plugins/build/plugins) in Work/Codex desktop. These are distinct paths. Neither establishes native Voice tool invocation in a free teen account.

## Copyable bootstrap prompt

Use this in a coding-capable chat on the intended person's own Windows computer/account. It cannot install through ordinary Voice alone.

> Set up Emma from the private GitHub repository https://github.com/heroyuer/Emma for this account. Read AGENTS.md, README and docs/installation.md first. Verify my own GitHub read access; never use the parent's credentials. Check this host's supported local plugin/marketplace commands and Google Drive capability. Use only an approved stable release by default; if none exists, report that and stop before installing a preview unless I explicitly ask to test it. Run the release's tests and verification, then scripts/bootstrap.mjs to stage/activate the local plugin and merge its marketplace entry without disturbing other entries. Keep learner identity, Drive folder IDs and active-session state outside the package under my profile. Register the included daily/sign-in update task only on this machine/current Windows account. Ordinary approved future upgrades are authorized automatically, without asking each time. Do not interrupt an active lesson, claim hot reload, share this plugin publicly, or create a Sites server. Explain the required restart/Plugins install step and my own Drive sign-in. Ask for the newly designated archive folder and preferred first name/stable learner label if missing. Verify the full skill and Drive write/readback before calling setup complete, and separately test a fresh native Voice chat saying Hi Emma and a clear stop saving the actual available transcript. If this is Work/Codex only and native Voice cannot use it, report that blocker rather than claiming it meets the requested experience.

Parent preview testing: clone the private repo with the parent's own GitHub sign-in, inspect the exact source, then `node scripts/bootstrap.mjs --preview`. Preview is opt-in, never the children's default updater channel. Restart the desktop client and install Emma from the local marketplace. A marketplace entry makes the plugin discoverable; it does not prove installation/connection or Voice support. The first preview is tagged `emma-v0.1.0` only as a tested source package, not a shipped cloud plugin.

Account-owned alternative, only where available: attach the current tested `dist/Emma-<version>.tar.gz` to Plugin Creator in that child's own account and request a private Emma plugin from the archive, including its standard Drive dependency, with no Site/custom server. Inspect returned files/version/dependency and complete installation/connection. Do not copy the old private Site App ID. We have not performed this in the children's accounts. This route does not inherit local automatic updates: each account's same plugin ID must be updated through that account's supported Plugin Creator workflow.

Do not create duplicate plugins as a failed-install workaround. Record the actual account-owned plugin ID outside Git and use guarded expected-release updates. If no supported authoring/install interface exists, installation is blocked; the archive alone is not success.

For existing installs, use [the current child update guide](UPDATE_EMMA.md); do not repeat bootstrap or create another plugin.
